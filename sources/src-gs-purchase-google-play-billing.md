Vendor policy changes often; re-fetch before promoting dependent notes to `verified`. Not legal advice. No synthesis here.

- **Security best practices:** "Move sensitive logic to your backend" ("an online chess game should validate all moves in the backend instead of trusting that the frontend always sends legal moves"). **Verify purchases before granting entitlements:** send the `purchaseToken` to your backend and keep a record of all tokens; "Verify that the purchaseToken value for the current purchase does not match any previous purchaseToken values. purchaseToken is globally unique, so you can safely use this value as a primary key in your database"; verify with `Purchases.products:get` or `Purchases.subscriptionsv2:get`; check `obfuscatedAccountId`/`obfuscatedProfileId` matches the expected user; if validation fails "don't grant entitlement and don't acknowledge or consume the purchase" and refund explicitly via `orders.refund` with `revoke=true` (or `subscriptionsv2:revoke`). "Don't grant entitlement when the purchase state is PENDING." "Don't use orderId to check for duplicate purchases or as a primary key … purchases made with promo codes don't generate an orderId." Acknowledge/consume from the server (`Purchases.products:consume` / `:acknowledge`): "if the user does not log back in within three days, the purchase is automatically refunded due to lack of purchase acknowledgement." Unlocked content: do not bundle it in the APK; deliver from a server. **Voided purchases:** cancelled (by user, developer or Google incl. unacknowledged auto-cancel), charged back, or refunded with the "revoke" option; responses: clawbacks (set currency negative if already spent), multiple strikes, temporarily disable purchases, disallow access in extreme cases, poll the API more often. `setObfuscatedAccountId`/`setObfuscatedProfileId` help Google "detect suspicious behavior and block some types of fraudulent transactions". Verify purchase state whenever remote-served content is accessed.
- **Integrate (life of a purchase):** 1 show products, 2 launch the billing flow, 3 "Verify the purchase on your server", 4 give content, 5 acknowledge; "For consumable products, consume the purchase so that the user can buy the item again." Product kinds on the page: one-time products split into consumable and non-consumable, plus subscriptions (states Active, Cancelled, In grace period, On hold, Paused, Expired). Acknowledgement must be "within three days so that the purchase isn't automatically refunded"; "The three-day acknowledgement window begins only when the purchase state transitions from 'PENDING' to 'PURCHASED'". Consumables: with a backend prefer `Purchases.products:consume`, otherwise `consumeAsync()`; non-consumables: `Purchases.products:acknowledge` or `acknowledgePurchase()`. Pending transactions (`enablePendingPurchases()`, mandatory for one-time products): check `getPurchaseState()` is `PURCHASED` before granting; a user may complete a pending payment while the app is not running (RTDN keeps the backend in sync). Rejected purchases: "Never call consumeAsync(), acknowledgePurchase(), Purchases.products:consume, or Purchases.products:acknowledge on rejected purchases."
- **`purchases.products.get`:** `GET https://androidpublisher.googleapis.com/androidpublisher/v3/applications/{packageName}/purchases/products/{productId}/tokens/{token}`; scope `https://www.googleapis.com/auth/androidpublisher`; sample response fields `kind`, `purchaseState`, `consumptionState`, `acknowledgementState`, `orderId`, `purchaseToken`, `obfuscatedExternalAccountId`, `purchaseType`, `regionCode`, `developerPayload` (meanings of the numeric values are on the linked `ProductPurchase` page, not read). No deprecation note seen; the RTDN page references a newer `purchases.productsv2` endpoint.
- **Voided Purchases API:** lists orders voided by user refund, user cancellation, chargeback ("includes payment-processor chargebacks"), developer refund **with the revoke option**, or Google. Only purchases voided in the **past 30 days** are returned regardless of `startTime`; `maxResults` ≤ 1000; `type` 0 = in-app, 1 = plus subscriptions. Quota: 6,000 queries/day per package (resets midnight Pacific), 30 per 30 s. "Use this API as one of many elements in a comprehensive strategy to address undesired behavior"; combine with RTDN; apply a staged, transparent, uniform policy.
- **RTDN reference:** Cloud Pub/Sub message with base64 `data` → `DeveloperNotification { version, packageName, eventTimeMillis, oneTimeProductNotification | subscriptionNotification | voidedPurchaseNotification | pendingRefundReviewNotification | testNotification }` (mutually exclusive). "You must call the Google Play Developer API after receiving Real-time developer notifications to get the complete status … These notifications tell you only that the purchase state changed." Check `messageId` uniqueness to avoid duplicate processing. `OneTimeProductNotification` types: (1) `ONE_TIME_PRODUCT_PURCHASED`, (2) `ONE_TIME_PRODUCT_CANCELED`; fields `purchaseToken`, `sku`. `VoidedPurchaseNotification`: `purchaseToken`, `orderId`, `productType` (1 subscription, 2 one-time), `refundType` (1 full, 2 quantity-based partial). `PendingRefundReviewNotification`: chargeback requests needing a developer answer "within 24 hours by calling the ReviewRefund API". Subscription types include `SUBSCRIPTION_PURCHASED` (4), `RENEWED` (2), `CANCELED` (3), `ON_HOLD` (5), `IN_GRACE_PERIOD` (6), `REVOKED` (12), `EXPIRED` (13), etc.
- **Play Integrity API overview:** verdicts for "genuine app, installed by Google Play, running on a genuine and certified Android device": `accountDetails` (`appLicensingVerdict` = `LICENSED`), `appIntegrity` (`appRecognitionVerdict` = `PLAY_RECOGNIZED`), `deviceIntegrity` (`MEETS_BASIC_INTEGRITY` < `MEETS_DEVICE_INTEGRITY` < `MEETS_STRONG_INTEGRITY`), optional `appAccessRiskVerdict`, `playProtectVerdict`, `recentDeviceActivity`, `deviceRecall` (beta). "The Play Integrity API works best when used alongside other signals as part of your overall anti-abuse strategy and not as your sole anti-abuse mechanism." Default quota "up to 10,000 total requests per day across all installs". Standard requests (fast, `requestHash` content binding) vs classic (slow, `nonce`); verdicts are decrypted/verified on your server; "Avoid caching integrity verdicts"; tiered enforcement, "Send a range of responses from your server to your app"; plan for outages.
