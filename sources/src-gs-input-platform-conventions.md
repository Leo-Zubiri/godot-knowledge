Apple's HIG pages were read from their JSON data endpoints (`/tutorials/data/design/human-interface-guidelines/game-controls.json`, `accessibility.json`), which carry the same text as the rendered pages. There is **no public console certification text** here; platform conventions are vendor design guidance, not requirements. Re-fetch before promoting dependent notes to `verified`. No synthesis here.

- **Microsoft, "Gamepad and remote control interactions" (UWP, 2020-09-24):** built-in keyboard→gamepad mappings: Arrow keys → D-pad (also left stick), Spacebar → A/Select, Enter → A/Select, Escape → B/Back ("If the B button is used to go back, then don't show a back button in the UI"). Accelerators: Page up/down → left/right **triggers**; Page left/right → left/right **bumpers**; Zoom → triggers; open/close nav pane → View; Search → Y; context menu → Menu (right-click on PC). Buttons: A/Select, B/Back, D-pad, Menu, View exist on both gamepad and remote; X/Y, sticks, triggers, bumpers are gamepad-only ("using them for critical interactions may create a situation where the user is unable to interact"). XY focus navigation: ensure every element is reachable (no overlapped focusables, middle-of-four-corners layouts unreachable), "path of least clicks", put initial focus top-left, focus visual always visible ("there should be a focusable item onscreen at all times"), focus engagement (press A to engage sliders/lists, B to disengage) to avoid focus trapping, "mouse mode" for free-scrolling content such as maps. "A good way to ensure that your app will work well with gamepad/remote is to make sure that it works well with keyboard on PC."
- **Apple HIG, "Game controls":** "A game controller is an optional purchase … If you support game controllers, try to make sure there's a fallback for using the platform's default interaction method." tvOS/visionOS may require a controller (`GCRequiresControllerUserInteraction`, "Game Controller Required" badge). "The Game Controller framework assigns standard names to controller elements based on their placement, but the colors and symbols on an actual game controller may differ. Be sure to use the connected controller's labeling scheme"; with several controllers "use labels and glyphs that match the one that the player is actively using"; "Prefer using symbols, not text" (SF Symbols per brand). **UI (non-gameplay) conventions "across all Apple platforms":** A activates a control; B cancels or returns to the previous screen; left/right shoulder navigate between screens/sections; sticks and D-pad move selection; Home/logo "Reserved for system controls"; Menu "Opens game settings or pauses gameplay"; X, Y, triggers unassigned. **Touch controls:** place frequently used controls at a minimum of 44x44 pt and less important ones (menus) at 28x28 pt; "Always include visible and tactile press states"; avoid "controller-based naming like A, X, or R1 as artwork"; show/hide virtual controls to reflect gameplay; "show a virtual thumbstick wherever the player lands their thumb instead of a static thumbstick position"; for camera "use direct touch to pan the camera instead of a virtual thumbstick". **Keyboards:** "Prioritize single-key commands"; "Let players customize key bindings." No separate rule for confirm/back **during gameplay**; no remapping guidance for controllers.
- **Apple HIG, "Accessibility":** control size table — iOS/iPadOS default 44x44 pt, **minimum 28x28 pt**; macOS 28/20; tvOS 66/56; visionOS 60/28; watchOS 44/28 (so 44 pt is the *default*, not the minimum). "Consider spacing between controls as important as size" (~12 pt padding around bezelled elements, ~24 pt without bezel). "Make sure your UI's core functionality is accessible through more than one type of physical interaction … if you use a swipe gesture to dismiss a view, also make a button available"; "avoid custom multifinger and multihand gestures". Reduce Motion: reduce automatic/repetitive animations; Dim Flashing Lights. Contrast (WCAG AA): 4.5:1 up to 17 pt, 3:1 at 18 pt or bold. "Convey information with more than color alone." Text: allow enlargement "by at least 200 percent". Games: "consider adding the ability to customize the difficulty level … reduce the criteria for successfully completing a level, adjust reaction time, or enable control assistance"; "Augment audio cues with visual cues"; pair audio feedback with haptics; captions for cutscenes.
- **Android accessibility help, "Touch target size":** interactive elements should have "a width and height of at least 48dp" (Material guidance), "separated by 8dp of space or more"; 48 dp ≈ 9 mm, recommended range 7–10 mm; the touch target may include padding around a smaller (e.g. 24 dp) icon. (The Material 3 page requested for this figure returned 404.)
- **WCAG 2.2 SC 2.5.8 Target Size (Minimum), Level AA:** "The size of the target for pointer inputs is at least 24 by 24 CSS pixels, except when:" Spacing (a 24 px circle on each target does not intersect another), Equivalent, Inline, User Agent Control, Essential. SC 2.5.5 Target Size (Enhanced) "uses the larger 44 by 44 CSS pixel measure as its threshold size" (AAA, recommended for important controls).
- **Steam Deck compatibility review:** badges Verified ("passes all compatibility checks"), Playable (works but needs manual user work such as selecting a controller config or invoking the on-screen keyboard), Unsupported, Unknown. **Input items:** "your game must support Steam Deck's physical controls"; "The default controller configuration must provide users with the ability to access all content"; "Players must not need to adjust any in-game settings in order to enable controller support"; "On-screen glyphs must match the inputs being used, whether it's Deck, Steam Controller, or Xbox glyphs"; "Mouse and keyboard glyphs should not be shown if they are not the active input"; text entry must use a Steamworks text-entry API to open the on-screen keyboard or a built-in controller-only entry; launchers need "Full navigability with a controller" (Valve "recommend[s] strongly against requiring the user to navigate a launcher"). Display: 1280x800 (preferred) or 1280x720; smallest font ≥ 9 px tall at 1280x800; default config ≥ 30 fps at 800p.
- **Steam Input, "Getting Started for Developers":** the API is "designed to allow you to easily enable *full support* for Steam Input devices in your game"; full support includes "Your game uses the proper controller-specific glyphs when showing in-game input prompts"; Action Sets ("all the actions a player can take within some game context": menus, on-foot, vehicles) and Action Set Layers (inherit the parent's settings); digital (`bState`) and analog (`x,y` depending on the IGA mode) actions; the IGA file lists action sets in KeyValues format; limits "16 analog and 128 digital actions"; `GetGlyphForActionOrigin` returns a local `.png`/`.svg` path, "supports all hardware devices recognized by Steam Input", poll origins each frame rather than caching. "When Steam is sending gamepad input it will appear in your game as regular Xbox controller input" (gamepad emulation, also via Remote Play or user reconfiguration), and USB device-ID checks "will not work" then. The store-page labels "Full"/"Partial Controller Support" were **not defined on the pages read** (*unverified*).
- **SDL_GameControllerDB (mdqinc; the SDL-mirror URL 404s):** "A community sourced database of game controller mappings to be used with SDL Game Controller functionality" (SDL2 and SDL3); one line per controller: GUID, name, assignments such as `a:b1`, `leftshoulder:b4`, `dpdown:h0.4`, `leftx:a0`, `lefttrigger:a2`, then `platform:…`; field names seen: `a b x y back guide start leftstick rightstick leftshoulder rightshoulder dpup dpdown dpleft dpright leftx lefty rightx righty lefttrigger righttrigger`; contributions should "best represent the Xbox layout per the mapping guide"; load with `SDL_GameControllerAddMappingsFromFile("gamecontrollerdb.txt")` (SDL2) / `SDL_AddGamepadMappingsFromFile` (SDL3); SDL ≥ 2.0.10; **Zlib licence**.
- **Kenney, "Input Prompts" (2024, Creative Commons CC0):** glyphs for Xbox 360/One/Series, PlayStation 1–5, Steam Deck/Steam Controller/Steam Frame/Valve Index, Nintendo Switch/Switch 2/Wii/Wii U/GameCube, Meta Quest 1–3, Playdate, keyboard & mouse, touch gestures, generic controls, flairs; 64x64 tiles; "1500×" files; v1.4 "Added spritesheets and fonts". Free, donations optional.
- **Hoober, "How Do Users Really Hold Mobile Devices?" (UXmatters, 18 Feb 2013):** 1,333 public observations over two months (780 touching the screen); no demographics, tasks or device models recorded. Among screen-touchers: one-handed 49% (right thumb 67%, left 33%); cradled 36% (thumb 72%, finger 28%); two-handed 15% (portrait 90%, landscape 10%). Thumb-reach "green/yellow/red" zones vary by person, grip and phone size; grips change "every few seconds"; the author calls it not "the ultimate study". **Later correction in the author's own comments (2017): "Please, please everyone ignore those drawings"** — the edge-touch claim was wrong, people touch the centre more; the editor's note says the guidelines were updated after further research. Treat the grip percentages as a dated observation, not a standard.
